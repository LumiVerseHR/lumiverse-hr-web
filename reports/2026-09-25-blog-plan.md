# Blog on lumiverse.hr — analysis and plan

2026-09-25 · status: proposal, nothing built

## 1. Why now, and what the blog is for

The site already shows *what* we built: 12 case studies, a product (Titlomat) and a research band (air-laser). It does not show *how we think*. That gap matters because the studio's pitch is range ("small studio, unreasonable range"), and range is hard to prove with portfolio cards alone.

A blog fixes three things:

1. **Proof of method.** Case studies are polished outcomes. Posts can show the reasoning: the retraction in air-laser, the parity gate in Rentalica, why a 10-second consent timeout grants nothing.
2. **Search surface.** 32 pages, all about us. Posts rank for the problems people search for ("GPT-4o-mini WordPress translation cost", "Croatian YouTube subtitles"). Right now no page targets those queries.
3. **A home for writing that already happens.** There's a Medium article on air-laser, LinkedIn posts, and a Croatian Lider column. None of it builds equity on lumiverse.hr.

**One editorial through-line** (already the site's thesis): *the moat is the verifier, not the generator.* Almost every project has a verifier story. Posts don't have to be about it, but it gives the blog one recognisable voice rather than a topic grab-bag.

**What it is not:** an SEO content farm. Thin, AI-padded posts would damage a site whose whole pitch is judgement. Two good posts a month beat eight forgettable ones.

## 2. What the codebase means for the build

The site is an Astro 7 project in "wrapper" mode. That shapes the options:

| Fact | Consequence for a blog |
|---|---|
| Pages are hand-written `*.html`, copied into `src/pages/` by `tools/migrate-to-astro.mjs` | Writing each post as a full HTML page means ~600 lines of chrome per post. Doesn't scale. |
| `migrate` runs `resetDir(src/pages)` on every build | Any real `.astro` route placed in `src/pages/` gets **wiped**. Blog templates must live elsewhere and be copied in, or `resetDir` must be narrowed. |
| Nav/footer/consent are single-sourced in `partials/` and pushed into HTML by `sync_shared.py` | An Astro layout can **read the same partials at build time**, so there's still one source of truth and no drift. |
| `styles.css` is content-hashed by migrate (`/styles.<hash>.css`) | The layout needs the hashed name. Migrate should write a tiny manifest (e.g. `src/generated/assets.json`). |
| `sitemap.xml` is hand-maintained | Hand-adding every post is a guaranteed miss. Generate post entries at build time. |
| `test:seo` scans everything in `dist/` (title 30–65, description 110–165, sitemap membership, no duplicates) | Posts get SEO checks **for free**, and will fail the build if they're missing from the sitemap. Good. |
| `test:i18n` pairs a **hardcoded** slug list | Posts aren't forced to have a translation. That's the right default (see §4). |
| No RSS feed anywhere | Must add one. It's table stakes for a tech blog, and it feeds IndexNow/aggregators. |

**Recommendation: Astro content collections.** Posts become Markdown files with typed frontmatter. One layout renders them. This is the first real Astro feature the site would use, and it's the reason Astro was adopted.

```
src/content/blog/en/verifier-not-generator.md
src/content/blog/hr/...
src/content.config.ts        # schema: title, description, date, lang, tags, related, draft, translationOf
src/blog/                    # layout + routes, copied into src/pages by migrate (survives resetDir)
  BlogLayout.astro           # reads partials/*.html for nav/footer/consent, fills {{alt_url}}
  blog/index.astro           # /blog
  blog/[slug].astro          # /blog/<slug>
  hr/blog/index.astro        # /hr/blog
  hr/blog/[slug].astro
  rss.xml.js                 # /blog/rss.xml (+ /hr/blog/rss.xml)
```

The schema is the quality gate. Astro validates frontmatter at build time, so a post with a 170-character description or a missing date fails the build, just as a bad case study fails `test:seo` today. (Verify the exact content-layer API against the Astro 7 docs at implementation time.)

Rejected alternatives:
- **Hand-written HTML per post.** Matches the current site, but costs ~1 hour of boilerplate per post and bypasses every check except SEO.
- **Headless CMS (Ghost, Sanity, WordPress).** A second system to host and secure, for a writing volume of a few posts a month. The Markdown-in-git workflow also suits AI-assisted drafting and PR review.
- **Keep posting on Medium and link to it.** Zero SEO equity for lumiverse.hr. Medium becomes the *syndication* target instead (see §6).

## 3. Page design

It reuses the existing system (dark glass, Inter, coral/cyan). Nothing new visually except typography for long-form reading.

- **`/blog` index.** Section header in the house style (label + gradient headline, e.g. "Notes From the Workbench"). Newest post as a large bento card, then a grid. Filtering by tag is phase 2, not launch.
- **Post page.**
  - Breadcrumb, tag pill, title, date, reading time, author.
  - Body column capped at ~70ch. `styles.css` currently has no prose styles, so this needs new rules (headings, lists, blockquote, code, tables, figures) under a `.prose` scope.
  - Code blocks via Astro's built-in Shiki highlighting: zero client JS, themed to the palette.
  - End-of-post block: "Related work" linking the case study the post draws on (`related:` in frontmatter), then the existing capacity-note / contact CTA.
  - `Article` JSON-LD, canonical, OG/Twitter tags, `hreflang` only when `translationOf` is set.
- **Homepage.** A 3-card "Latest writing" strip, probably between Research and About. It's generated from the collection, so it never goes stale. That means the homepage needs to render one dynamic block. The cleanest way is a build-time placeholder (`<!-- blog:latest -->`) that migrate or a post-build step fills in, keeping `index.html` as the source of truth.
- **Nav.** Add one item. The name is an open question (§8). The nav already has 6 items, so check the mobile overlay and the 880px breakpoint.
- **Footer.** Add a link in `partials/footer.html` + `partials/hr/footer.html` → `sync_shared.py`.

## 4. Language policy

The site is fully bilingual page-for-page. Doing that for every post would halve output. Recommendation:

- **Write in the audience's language, translate only when it earns it.** Most technical posts are EN (international clients, dev audience). Posts about the Croatian market (fiskalizacija, Tvrtko/Pazi data, local SMEs) are HR-first.
- Each language index lists only its own posts. A translated pair links via `translationOf`, which drives `hreflang` and the language switcher. An untranslated post's switcher points to the other language's `/blog` index, not a 404.
- The Lider column is an HR source. A column can become an HR post (check the publication's reuse terms first) or an EN adaptation.

## 5. Content: pillars and a seed backlog

Four pillars, all mapped to things we have actually built:

| Pillar | What it covers | Draws on |
|---|---|---|
| **Build logs** | How a specific system was built, with numbers | Rentalica, Country Guides, Lider Translations, Army Adria, Barcoder |
| **Agentic engineering** | Agents, MCP, verifiers, Claude Code workflows, where AI coding breaks | air-laser station, Overserved, Moj Kolega, harness/agentic-factory work |
| **Research notes** | Shorter companions to the Research band | air-laser (and whatever follows it) |
| **Web craft** | Small, sharp, practical posts | consent gating, content-hashed assets, the Astro wrapper migration |

**Seed backlog** (✓ = material already exists; the first three are the launch set):

1. ✓ **"The moat is the verifier, not the generator."** The thesis post: four projects, four verifiers (Overserved balance bot, Aimito vision-QA, Rentalica parity gate, air-laser critic + retraction). Anchors the whole blog.
2. ✓ **"Eleven WordPress sites, ten languages, one newsroom."** Lider Translations: pipeline, GPT-4o-mini cost per article, what translation gets wrong. Strong search intent.
3. ✓ **"A cookie banner that doesn't pretend."** This week's work: why a timeout isn't consent, the GA cookie that re-wrote itself during the reload, the partial-sync system. Short, practical, and very linkable.
4. ✓ Air-laser: republish the Medium article here with a canonical link, and re-point Medium at it.
5. ✓ Rentalica: rebuilding a decade-old PHP system as multi-tenant SaaS, and the parity gate that made it safe.
6. ✓ Country Guides: 12 branded sites from one codebase. What stays shared, what stays per-tenant.
7. ✓ Army Adria: what one non-developer shipped in two weeks with AI, and where it needed a human.
8. ✓ Moj Kolega: grounding a webshop agent in the catalogue so it can't invent products.
9. ✓ Overserved: how far AI-assisted game dev goes.
10. Migrating a hand-written site to Astro without rewriting a page (the wrapper approach).
11. HR: fiskalizacija / partner risk through Pazi.ai data (HR-first).

**Confidentiality rule.** Client engagements (Bridj, anything under Reed/yaoki) get a post only after the client signs off on the text. Default to our own products and research.

**AI-assisted drafting is fine; AI-authored posts are not.** Every post needs real numbers, a real decision and a real mistake. That's also what the writing guide asks for ("specific numbers, concrete benefits"). A topic-backlog skill modelled on `lider-article-topic-discovery` could mine commits, reports and case studies for candidate posts. It's worth building once the blog exists, not before.

## 6. Distribution

- **Canonical on lumiverse.hr, always.** Medium (import tool keeps `rel=canonical`), LinkedIn post with the link, dev.to where relevant.
- **RSS** at `/blog/rss.xml`, advertised with `<link rel="alternate" type="application/rss+xml">` on every page.
- **IndexNow** runs automatically after deploy (existing convention). It reads `dist/sitemap.xml`, so posts get submitted once they're in the generated sitemap.
- **Analytics.** Already consent-gated. Clarity shows whether posts are actually read (scroll depth), and GA shows which ones pull search traffic. Review after ~8 posts, not before.

## 7. Phased plan

**Phase 0: decisions (you, ~30 min).** Answer the open questions in §8.

**Phase 1: infrastructure (~1–1.5 days, one PR)**
1. Narrow migrate's `resetDir` (or copy `src/blog/` into `src/pages/` after the reset). Emit `src/generated/assets.json` with the hashed asset names.
2. Content collection + schema (`src/content.config.ts`).
3. `BlogLayout.astro`: reads `partials/` for nav/footer/consent, fills `{{alt_url}}`, loads hashed CSS, `consent.js`, and the nav scripts.
4. Routes: EN/HR index + post pages, RSS.
5. Sitemap: generate post `<url>` entries at build time (finalize step appends them to `dist/sitemap.xml`).
6. `.prose` styles + Shiki theme in `styles.css`.
7. Nav + footer partials + sync. Homepage "Latest writing" strip.
8. Tests:
   - `test:seo` already covers posts.
   - Extend `test:routes` to cover `/blog`, a post and `/blog/rss.xml`.
   - Extend `test:i18n` to check that `translationOf` pairs are reciprocal.
9. Ship with one real post, not lorem ipsum. Nothing goes live half-empty.

**Phase 2: launch content (~1 week of writing, spread out)**
- Posts 1–3 from the backlog. Launch when all three are ready, so the index isn't a single lonely card.
- Air-laser canonical republish.

**Phase 3: cadence**
- Target 2 posts/month. Review traffic and reading depth after ~8 posts, then decide on tag pages, series, a newsletter, or an HR expansion.

## 8. Open questions (yours to decide)

1. **Name + URL.** Options: "Blog" `/blog` (clearest), "Notes" `/notes`, "Writing" `/writing`. My recommendation is **Blog at `/blog`**, with a house-style headline on the index page to give it character.
2. **Author voice.** Posts by you personally (byline, photo) or by "LumiVerse"? A personal byline reads better and ranks better (E-E-A-T), so I'd recommend that.
3. **Default language.** EN-first with selective HR, as proposed in §4?
4. **Medium.** Keep syndicating there with canonicals, or stop?
5. **Which three launch posts.** The proposed set is the verifier thesis, Lider Translations, and the consent banner.
